# OS — Claude Code Rules

## Formatting

After editing any `.ts`, `.tsx`, `.js`, `.jsx`, `.css`, or `.json` file, run prettier on the changed files before committing:

```bash
pnpm prettier --write <changed-files>
git add -u
```

The pre-commit hook does this automatically, but running it upfront avoids formatting noise in diffs. The project uses `prettier-plugin-tailwindcss`, so Tailwind class order is enforced too.

See `.claude/skills/prettier-format.md` for full details.

## Code comments — only when necessary

Comments are a cost. Most well-named code needs none. Do not narrate the code — prefer clear names over prose that restates what the code already says.

Add a comment ONLY to capture what the code cannot:

- A non-obvious **why**: a rationale, trade-off, or business rule that isn't visible from the code.
- A **gotcha or workaround**: why something is done an unusual way (ideally with a ticket/link).
- A **warning**: a non-obvious consequence or ordering requirement.

Do NOT add:

- Comments that describe the next line (`// set the tenant`, `// loop over items`, `// fetch the data`).
- Restatements of signatures, types, or obvious control flow.
- Section-banner or decorative comments.
- Scaffolding/attribution/changelog notes (`// added by …`, resolved `TODO`s, "this now does X").

When in doubt, leave it out. If deleting a comment loses nothing a competent reader wouldn't get from the code itself, delete it. This applies to code you write **and** code you edit — don't leave behind noise.

## Git push — --no-verify is NEVER allowed

Never use `--no-verify` when committing or pushing. The pre-push hook runs typecheck, lint, build, unit tests, and e2e coverage checks. These are required. If a hook fails, fix the root cause.

Only exception: the user explicitly instructs it in the current message.

See `.claude/skills/safe-push.md` for the full push protocol and how to handle each failure type.

## Bug fixes require regression tests

Every bug fix lands with tests that would have caught the bug: a unit test in the same change (vitest for TS; the touched module's `mod tests` for Rust — pre-push runs `cargo test` when `src-tauri/*.rs` changed), and, when the bug was user-visible, an e2e checkpoint. A fix without a test that fails on the pre-fix code is not done.

See `.claude/skills/e2e-coverage.md` for when and how to add the e2e half.

## E2E coverage

After any change to user-facing behavior, evaluate whether `e2e/coverage.json` and `e2e/COVERAGE.md` need updating. Coverage must never regress.

See `.claude/skills/e2e-coverage.md` for the full decision process.

## Startup performance — don't block first render

The startup path was deliberately unblocked: nothing on the way to first render
may `await` data that the UI reads reactively. Before adding an `await`, a
provider, or a query that runs on load, check what the screen shows while it
waits — if the answer is "a spinner" or "nothing", that is a regression.

Three places must stay unblocked: `redirectToMentor(...)`, `setIsLoading(false)`
/ `onComplete?.()` in the providers, and `<SdkChat>` rendering unconditionally
in `mentor-page-content.tsx`.

Deferring has traps that have already been hit: an empty permissions object
means both "denied" and "not asked yet" (two consumers fail OPEN on it), and
`await` was silently providing ordering that fire-and-forget gives up.

See `.claude/skills/startup-performance.md` before touching the load path.

## UI terminology: "users" not "students", "agent" not "mentor"

We moved from "student" to "user" and from "mentor" to "agent". This is a UI rule: everything a person reads (UI strings, all locales, toasts, errors, dialog titles) says "user(s)" and "agent(s)" — e.g. "User Models", "Edit Agent". It does NOT apply to API calls, endpoint paths, request/response fields, query params, or existing code identifiers (`mentor_id`, `useGetMentorsQuery`, `useUserIsStudent`, …) — never rename those to match the copy.

## UI casing: match the screen you are extending

The app has an established capitalization style per surface, and new UI must copy it — check the neighbouring labels before writing copy. Most labels a person clicks or scans (tab and dialog titles, section headings, field/toggle names, buttons, menu items) use Title Case, as in the agent settings tab: "User Models", "Search Providers", "Allow All OpenAI Models", "Save Anyway". Small joining words (a, an, the, of, to, in, on, for, and, or, with) stay lowercase unless first. Full sentences — descriptions, help text, errors, toasts, counts like "3 of 29 allowed" — stay in sentence case. Brand/model names keep their own casing (ibl.ai, GPT-4o mini). Where a surface already does it differently, follow that surface, not this default.

## The user has never coded

Everything a user reads — UI strings, the Code agent's replies, errors we surface — is written for someone who has never coded: everyday words, what they get and what we need from them, never developer vocabulary (scaffold, repo, build, lint, typecheck, dependency, DNS, …) and never how something was made. For the Code agent that rule is the voice bullet of `IBLAI_INSTRUCTIONS` (`src-tauri/src/opencode_proxy.rs`), pinned by the `result-or-obstacle-only` guard; when a reply leaks jargon, extend that bullet — never a skill, and never the agent-facing text with words you would not want echoed. For the Code turn's own UI — the step list, the permission card's sentence, the working line — the text is built from ACP metadata by `describeStep` in the SDK (`@iblai/web-containers`, `src/components/chat/code-activity.tsx`), never from the reply — where the agent's own words do show (a step's short description, its task list) the step-label rule in `IBLAI_INSTRUCTIONS` keeps them plain; the OS only forwards the ACP events, so a new `sessionUpdate` kind reaches the webview only through `forwarded_update` (`opencode_acp.rs`), and a tool the describer cannot name falls back to "Finished a step" with the raw title behind the row's disclosure — extend the SDK's table rather than showing a raw title; developer-shaped Code errors map to plain sentences in the SDK's `code-error-text.ts`.

## UI simplicity: the common path needs no decisions

Every screen is for someone who has never configured software. Apply these rules to existing screens you touch, not only new ones, and before handing a screen over, use it as that person would: if they would give up rather than finish, it is not done. This came from Miguel's review of the agent-settings MCP tab (iblai/iblai-platform#2725, October 2026): a switch beside a Connect button and sign-in chips was confusing ("Dumb it down. We don't want people to have to think too much"); a switched-on connector should simply be connected; a card needs "a toggle to turn it on or off and another thing to edit the configuration"; its actions must match its switch ("If we do words, then we should do words, and if we do icons or toggles, then we should carry that philosophy out"); and tab names must read well. Shared UI lives in the SDK, whose CLAUDE.md (iblai-web-frontend) has these rules with examples; change both together.

- **On means working.** A switch is the whole decision: turning something on works in the same click and starts what is missing without slowing the switch (a sign-in opens in a new tab). No "turn it on first", no dialog on every toggle, no Connect button on any row: a switch whose sign-in is missing shows off and turning it on starts that sign-in (agent settings and the chat panel alike); offer only the sign-in this person can complete and the app can see (the chat handles each person's own sign-in; shared ones stay with the agent settings cards, since only tenant admins can make or list them). Connect and Disconnect for an item that is set up live in its settings form's Connection row, with an info tooltip saying whose account it is. A first sign-in window is explained once (whose account, allow pop-ups). When a change leaves it on but unable to work, turn it off in the same step and say so in one plain line with how to turn it back on.
- **One control per decision.** One primary control (a switch, or the one word button for the next step) plus at most a settings entry and Delete, in the row's own style. Never extra chips or buttons, never two controls for the same thing (a switch plus a "for all my chats" link), never a "..." menu. Actions stay together, beside the switch or in one row below the content; one never wraps alone onto the next line and they never stack in a column. Remove controls instead.
- **Words or icons, carried through.** Beside a switch, actions are icons (gear, bin) with a tooltip and an accessible name, and the card is a group named after its item; a row of word buttons stays all words. A word survives beside a switch only for the one step a person must take next (Select in a picker, in its own row below).
- **Hide what is not allowed** on a row (a button the person may not use) and show no empty button row; a switch fixed for them stays visible and locked, with the reason as its hover text ("Required by your organization"). A switch shows its own state: its words are its hover text and accessible name, the same words everywhere (on/off, never active/inactive or enabled/disabled, toasts included), in the blue the neighbouring switches and selected radios use. Hide an entry point with nothing behind it, and where people use something (the chat "+" menu), list only what is on for them.
- **One form, with what you may change enabled.** When only some settings may change, open the same form with those fields enabled and the rest disabled, never a separate dialog. Each setting is changed in one place; elsewhere it shows read-only (a word and an icon, with a tooltip saying what it means and, when they can, where to change it), and only where it applies.
- **Ask only when the automatic way fails.** Work out what the app can instead of asking: no "Automatic / Manual" tabs and no pickers for what the app can work out. Extra fields appear only when automatic setup needs them, at the end of the form after the setting they complete, only the required ones (optional ones under a closed Advanced section); never "contact someone" for what people can enter. When the fields could not help (no answer, address not allowed, too slow), show none: one sentence under the field says what to fix and, if that is why they are missing, that they appear once it works; a failure that may pass on its own leaves the button on to try again. Never offer two options that do the same thing.
- **Explain each field in place** with an info icon and a plain tooltip, using the SDK's Tooltip, never the native `title` alone (it shows late and never on a disabled control); the screen must still make sense without tooltips. Errors go under their field, named with the form's label, in a plain sentence, never raw backend text or a diagnostic box. One label size, control style and spacing top to bottom; a filter row shares one height.
- **Words.** Keep settled names (Authentication Scope, never "Sign-In") unless asked. Name a tab or list by what it really contains, from the person's side (check the query that fills it): the word the product already uses for the same idea ("Featured" for a list ibl.ai hand-picks, as on Explore), never one that suggests a per-person pick ("Recommended") when it is not, no sub-tab that only repeats what the whole tab is about, no name wrong for part of the list; siblings are short, Title Case pairs that never overlap, so the second is named for its own group, never "All" or "More" ("Featured" / "Directory"). Copy that points at a control names what the person sees ("the gear button"). State is a plain sentence or a read-only label, never a chip to decode. No jargon in sentences ("Organization", not "tenant"; "sign in", not "OAuth"); settled labels and options (Authentication Scope, Transport, OAuth) and names another service shows for a value people copy (Client ID, Redirect URI) stay.
- **Layout.** A list of cards is a two-column grid on wider screens, never one full-width card per row. Buttons size to their label, never stretched to fill a row (a filter row that stacks on narrow screens may span). Names wrap on cards, never truncate; no detail nobody uses, but a property the screen filters by is shown on the card, and a filter goes when its property does. Reuse the closest existing pattern (the "+" menu's Memory row, the Settings tab's sub-tabs) instead of inventing one.
- **OAuth sign-in links.** Open an MCP connector's `auth_url` as given; never rewrite its `redirect_uri` on the client, since providers accept only the registered callback (`invalid redirect_uri`). To test a sign-in on localhost, register a provider app with the localhost callback.

When a reviewer says a screen is confusing, remove controls and words before adding explanations.

## Code mode: ibl.ai instruction layers

Three OS-owned layers steer the Code agent (opencode, or Codex / Claude Code — see the paragraph after the list); each has guard tests pinning its load-bearing lines — update the pins in the same change as any text edit.

1. **Suppressor stub**: `src-tauri/src/opencode_build_prompt.txt` is TWO lines — identity plus the silence rule (no text before or between tool calls, one reply at the end), the one rule that needs the top-of-prompt slot — whose job is to exist: `enforce_build_prompt` writes it as `agent.build.prompt` + `default_agent: "build"` on every spawn, which suppresses opencode's built-in per-model prompts (they mandate step-by-step narration; upstream's `agent.prompt ? … : provider prompt` ternary means an EMPTY prompt would silently restore them — pinned by `the_build_prompt_is_a_minimal_suppressor_stub`). Never grow it back into a fork: everything else belongs in layer 2. The streaming path enforces the silence rule deterministically too: text the model emits before a tool call is reclassified into the reasoning section (`TurnState::take_narration`, `opencode_acp.rs`), so the visible reply is what follows the last tool call.
2. **The authored prompt — desktop policy + voice + working discipline**: `IBLAI_INSTRUCTIONS` in `src-tauri/src/opencode_proxy.rs` — the three asked setup steps (default template? → local preview at localhost:3000? → deploy?, plus the app’s name on the first deploy, which the agent turns into its subdomain, once per project, yes = auto-redeploy after; the deploy offer rides the preview reply and every deploy reply points at Open in Finder), the app named right after the template (package.json, the layout title, `NEXT_PUBLIC_APP_NAME`, the README) so the template's name never ships or deploys, nothing localhost- or deploy-shaped unasked, "our hosting" never "Vercel", RESOLVED env values, auto-minted `IBLAI_API_KEY`, the three-sentence reply cap, the plain-words voice rule for users who have never coded (what the app does, never how it was made) and the non-technical-user voice rule, the step-label rule (the short description the agent attaches to a command or side task, and every item of its task list, are shown to the user, so they are written in the same everyday words), and the working-discipline rules moved from the retired prompt fork (smallest correct change, ASCII, Glob/Grep + parallel reads, git safety: never revert others' changes / no `git reset --hard` / non-interactive git only). `guidance_with_identity` composes it with per-user identity lines at spawn; `write_iblai_guidance` (`opencode_acp.rs`) writes it as `<config_home(session)>/opencode/AGENTS.md` on EVERY spawn — unconditionally, skills wired or not, since it is the agent's entire authored behavior — strictly BEFORE `cmd.spawn()`, and a failed write aborts the spawn (opencode silently ignores missing instruction files, so never soften that error). opencode re-reads the file on every model call: main turns, subagents, ACP, and on-device (ollama/foundry) sessions alike. Never write that AGENTS.md outside the per-session ibl.ai config home (it is unrelated to this repo-root AGENTS.md). The retired delivery paths — loopback-proxy body injection and the config `instructions` key — must not come back.
3. **Skills**: vibe SKILL.md files sync from the LATEST vibe GitHub release at startup (or from the tag `IBL_VIBE_SKILLS_TAG` names — set it in `src-tauri/.env.local` to touch-test a vibe pre-release in a dev build). Portable procedures go there; desktop-only policy goes in layer 2, which supersedes skill wording.

**Codex and Claude Code.** The model string picks the agent — exactly `codex/default` → Codex (`@agentclientprotocol/codex-acp`), exactly `claude/default` → Claude Code (`@agentclientprotocol/claude-agent-acp`), anything else → opencode (`Backend::of` in `opencode_acp.rs`; exact strings, never a prefix, because a platform provider could be named `claude`). Both adapters are Node programs wrapping the vendor's native binary; the OS installs a pinned Node plus the pinned adapters into `~/.local/share/iblai` with npm (`code_agent_installer.rs`, Zed's recipe, SHASUMS-verified; own cache, blank npmrc files and every `npm_config_*` variable stripped — pnpm 10 exports the repo's `.npmrc`, `min-release-age=7` included, to `pnpm tauri:dev` as env) and runs everything by absolute path — nothing on the user's PATH is ever used. The agents need macOS 13.5 (Node v24's floor, `NODE_MACOS_MIN`): below it `supported()` is false, nothing downloads, and the popover's Agent row leaves them out. That install runs by itself, in the background, on every launch (`ensure_agents_current`, spawned in both twins' setup beside `ensure_opencode_current`; a pin bump therefore reaches every desktop on its next launch) and blocks nothing: `check_code_agent_status` reports `installing` while it runs, the popover shows that agent with a spinner and refuses the choice until its `code-agent:changed` lands (ibl.ai and any finished agent stay selectable), a turn on it fails with "still installing" (`agent_ready`), and a failed install shows its reason (`error`) with Install to retry — `install_with` returns early once the pin is installed, so a click queued behind the launch install never downloads twice. The model each agent runs is picked in the top-left while Code runs on it (`nav-bar/agent-model-selector.tsx`, an OS-only branch of the nav bar keyed on `useCodeAgent()`, opening the SDK's own `LLMProviderModal` in its `cloudOnly` mode — the LLM Selection dialog the cloud picker opens behind a provider card, so the two cannot drift; `@iblai/iblai-js` ≥ 2.28.0, whose `cloudOnly` keeps the device's Local Models setting out of it): saved per machine in `settings.json` (`code_agent_models`, `code_agent_models.rs`), listed from Claude's own ACP `configOptions` (captured on every handshake into `acp/<agent>/config-options.json`, or from a short probe session when nothing is cached — `probe_config_options`) and from Codex's CLI catalog (`codex debug models`, on every request), whose default is the model a fresh Codex session opens on (`remember_default`), applied with `session/set_config_option` right after the mode pin on every new session (a model the agent refuses fails the turn and names the picker — never a silent fall-back) and pushed to live sessions without a respawn (`push_config_option`); a pick a live session refuses is not saved, nor a Default the agent hasn't reported while a chat of it runs. They reuse the user's CLI logins (`~/.codex`, `~/.claude`, read through the adapters' CLI passthroughs) and the app has no sign-in of its own — a signed-out agent's popover line, toast and turn error say where to sign in: Codex in the ChatGPT desktop app, whose login the bundled Codex reads from `~/.codex` exactly as the CLI and the IDE extension do (macOS's official Codex install is that app, which puts no `codex` on the PATH); Claude Code with `claude` in a terminal; the sandbox binds only the chosen agent's own dir read-write, masks the other's, and re-binds the agent's CLI config (hooks, MCP servers, instructions, skills) read-only so a session cannot plant anything there for the user's next unsandboxed run (`Backend::frozen`; on Linux `freeze_missing` first creates the absent entries, since bwrap can't freeze a missing path) — not covered: a file those pull in from elsewhere in the login dir (a `CLAUDE.md` `@import`, a hook script), Claude's auto memory (`~/.claude/projects/<project>/memory/`), which shares the writable `projects/` with the transcripts `session/load` reads, and Codex's opt-in memories (`[features] memories`, off by default). Accepted consequences, by decision: the agent's shell can read its own subscription token, OS sessions appear in `codex resume` / `claude --resume`, and Claude loads the workspace's own `.claude/settings*.json` allow-rules. Layer 1 is opencode-only. Layer 2 reaches Codex as `developer_instructions` in `CODEX_CONFIG` and Claude as `_meta.systemPrompt.append` on `session/new` and `session/load` (appended to its preset, never replacing it), from ONE authored text with three per-agent substitutions (`substitute_for`, pinned by `each_agent_gets_its_own_wording`). Layer 3 reaches both as a per-spawn view of symlinks under `config_home(session)/agent-skills` sent as `additionalDirectories` (`link_skills`). The Approvals toggle — one mode for every chat, saved in `settings.json` (`permission_mode`; nothing saved is Automatic, so only a profile's Ask Me is ever seeded — saved once on a machine with nothing saved, via `seed_opencode_permission_mode`) — maps onto Codex's own modes — Ask Me → `read-only` (every write and network command escalates into a card), Automatic → `agent-full-access` (no Codex sandbox, no cards; the OS sandbox is the boundary) — pushed with `session/set_mode` on every flip and re-pinned after every spawn — a session that doesn't confirm is closed, and since codex-acp applies a mode from the next turn on, a switch from Automatic to Ask Me cancels a running Codex turn (`pin_codex_mode`); Claude is pinned to `default` and Automatic answers its cards. Permission answers pick the exact `allow_once` / `reject_once` kinds (`pick_option`): Codex lists `reject_always` before `decline`. A signed-out agent's JSON-RPC `-32000` becomes the `agent sign-in required` error, never a crash retry; `opencode_chat_stream` emits `opencode:auth_required` BEFORE the turn's `ollama:error`, `hooks/use-opencode-auth-required.tsx` shows the sign-in toast and `wasRecentAuthRequired()` keeps the generic chat toast quiet. Only `coding-mode-button.tsx` writes `ibl_coding_mode_model`; its Agent choice (`ibl_coding_mode_agent`, per machine, never synced to DM) stays hidden until `check_code_agent_status` answers, because the WebView runs the deployed web app and may face an older binary.

When `NODE_VERSION`, `CODEX_ACP_VERSION` or `CLAUDE_AGENT_ACP_VERSION` bumps (`src-tauri/src/code_agent_installer.rs`): re-verify codex-acp still merges `CODEX_CONFIG` into the session config (`developer_instructions`) and offers the `cli login status` passthrough, that claude-agent-acp still honours `_meta.systemPrompt.append`, `additionalDirectories` and `--cli auth status --json`, and that both still read `~/.codex` / `~/.claude`; then run `cd src-tauri && cargo test code_agent_pins -- --ignored --nocapture` (downloads the pins, ~700 MB) and the Tauri e2e checkpoint code-29. Every desktop pulls the new pins in the background on its next launch, so bump the three together, once.

When `OPENCODE_VERSION` bumps: re-verify upstream `session/instruction.ts` still loads the global AGENTS.md, then re-prove it empirically by running the always-on tests in `src-tauri/src/opencode_installer.rs` — `the_pinned_opencode_binary_is_reused_when_current_and_downloaded_when_not` (fetches the new pin into the managed bin dir when absent/stale) and `opencode_run_carries_the_agents_md_guidance_on_every_model_call` (drives the real pinned binary through two `opencode run` turns against a local stub and asserts every agent-turn model call carries the AGENTS.md guidance, rewritten between turns to prove the per-call re-read; the title-summarizer call is exempted by name and any unrecognized call type fails loudly): `cd src-tauri && cargo test pinned_binary -- --nocapture`. Then re-read `acp/tool.ts` and `acp/event.ts` at the new tag against `TOOL_VISIBLE_FIELDS` in `opencode_acp.rs`: the gate in `TurnState::admit_tool_update` forwards a tool update only when one of those fields changes, a `diff` content item rides along, or a failed call reports its error text — so the freeze returns if a listed field starts changing per chunk, and the UI goes stale if the SDK starts reading a field outside the list (today it reads `_meta.claudeCode.toolName` and `content[type=diff]`); extend the list — and `forward_tool_update`, which leaves out `rawOutput`, output text and the rest of `_meta` — in the same change as the SDK.

## Code mode: streaming to the WebView

**No per-chunk stream from an ACP session reaches the WebView one-for-one, and nothing is emitted from a tokio task directly.** Every per-chunk event in `src-tauri/src/opencode_acp.rs` passes a `TurnState` gate — `admit_tool_update` forwards a `tool_call` / `tool_call_update` only on a call's first update, when a field the UI reads changed (`TOOL_VISIBLE_FIELDS`: `status`, `title`, `kind`, `name`, `rawInput`, `locations`), when a `diff` content item rides along, or when a call that already failed reports its error text, and `forward_tool_update` sends the admitted update without `rawOutput`, output text or `_meta` beyond the tool name, which the chat never reads (opencode sends a finished call's whole output twice); `push_reasoning` batches thought chunks per `TOKEN_EMIT_WINDOW` as `pending_delta` batches reply text, and reply text flushes the batched thoughts ahead of itself — while once-per-action updates (a `plan`, a permission card) go out whole. Everything goes through `crate::emit_on_main`, and `opencode_chat_stream` flushes once at its single exit (`flush_emits`, bounded by `FLUSH_TIMEOUT`) because the SDK drops its listeners the moment `invoke` resolves — keep every return inside `chat_stream` so that stays true. A new per-chunk emit site without the gate re-creates the Code-turn freeze: opencode sends a `tool_call_update` per stdout chunk carrying the whole output so far, Codex a delta per chunk, and the WebView re-renders the chat per event until the command ends. A direct `app.emit` from a worker re-opens the `011d1707` deadlock: `tauri-plugin-devtools` forces tauri's `tracing` feature on in every profile, which makes every eval a blocking main-thread round-trip under the webview-manager mutex. `output_only_tool_updates_never_reach_the_webview`, `admitted_updates_carry_only_what_the_chat_reads`, `reasoning_chunks_are_batched_per_window` and `handle_update_forwards_only_what_the_webview_renders` pin the gate and its wiring — update them with it.
